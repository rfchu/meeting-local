# 采集所有权协议

当前新增 **E6 v2 独立控制服务**，见文末；下列 v1 保留为旧录音兼容说明。

## E5：写入者租约 v1

本轮建立身份、互斥与故障判定底座，没有实现 API 重启后连续采集的接管。协议适用于同一工作空间内的 build 3 采集器；不仲裁其他工作空间或第三方软件的音频设备。

## 身份与文件

API 为新录音生成 32 位十六进制 `capture_incarnation`，先连同录音 ID、`source=macos` 写入 session.json，再以参数传给采集器。采集器在打开设备前核对身份和活动会话状态，并独占该工作空间 recordings/capture-owner.lock。该锁由采集写入进程持有，不能由 API 的存活状态或 PID 文件替代。

采集器取得锁后，以私有 0600 临时文件、fsync 和重命名发布 capture-owner.json。内容包含协议版本、录音 ID、实例编号、工作空间路径摘要、PID、`transport=stdin_v1`、`reattach=false`；capture.json 同样携带实例编号。PID 仅用于诊断，实例编号用于关联，不是认证凭据。锁不随 exec 继承；进程退出或被强制结束后由内核释放。旧身份文件可保留，但不能证明进程还在写入。

## 判定矩阵

| 证据 | 判定 | 允许的动作 |
| --- | --- | --- |
| 锁空闲，旧身份文件仍存在 | saved_audio_only | 只按既有流程恢复已保存音轨；新采集器仍须重新获得锁 |
| 锁持有，身份一致，当前 API 持有该 Popen 子进程与 stdin | controlled | 使用已有 pause/resume/stop；退出确认和锁释放后才整理音轨 |
| 锁持有，身份一致，当前 API 没有原子进程句柄／stdin | controller_unavailable | 不自动接管、重复采集或整理该录音，不按 PID 发信号 |
| 锁或身份无法核对、实例与会话不符 | blocked_unknown_owner / blocked_identity_mismatch | 保守阻止新的原生采集，以及可能涉及未知写入者的音轨整理 |

v1 没有控制权转移。API 正常退出仍停止自己持有的采集器；API 崩溃使控制管道关闭，采集器在启动完成后观察 stdin EOF，执行既有收尾并退出。这个过程不是无缝续录，也不保证尚未落盘的音频能恢复。新 API 不会重放旧控制命令或使用旧 PID 终止进程。ASR 与采集写盘是独立生命周期，不因租约存在就判断识别正常。

两次并发启动在 API 预检查之后仍可能各自建立空会话，但采集器内核锁确保同一工作空间最多一个 v1 写入者打开设备；失败方按已有失败／空记录处理流程展示。旧版或外部采集器不遵守此协议，不能据此宣称被互斥保护。新开始入口要求 build 3 协议，历史音轨继续兼容既有恢复流程。

## 验证范围

测试用 Foundation/CryptoKit 单独编译 Ownership.swift，与真实采集器共享同一租约实现。测试写入者只写四字节合成 PCM，不导入音频或屏幕采集框架。覆盖锁竞争、未知／损坏／跨空间身份、只读检查、API 对象重建、拒绝无权控制和整理、写入者 SIGKILL、控制进程 SIGKILL→EOF→锁释放，以及音轨字节保持。已释放锁后的 PID 文件不参与接管授权。

真实三小时录音、系统睡眠／唤醒、麦克风被其他软件占用及原始中断原因仍待独立硬件验收。

## E6 后续边界

连续采集需要独立于 API 生命周期的控制服务和 v2 协议：工作空间绑定的本机 socket、同用户端点校验、采集实例握手、单一控制租约、命令序号与回执、旧控制者撤销、持久状态及明确的恢复控制动作。先用合成写入者验证 API 多次退出／重启仍写盘且不会重复采集，再考虑真实设备。不能把 v1 的 PID 或“服务已启动”升级为接管依据。


## E6：独立控制服务 v2（已实现）

新录音默认由独立 Python broker 启动并持有 build 3 采集器的 stdin。broker 使用独立进程会话，API 正常退出只释放控制租约，崩溃也不会关闭采集器管道。音频写入层继续使用 v1 内核租约；v2 描述的是控制层，不能将两个协议号混为一谈。旧 stdin 录音不做热升级。

### 边界与发现

控制端点位于当前用户缓存目录 `cn.seeknow.tingji/control/<工作空间与实例摘要>/c.sock`，目录 0700、socket 0600；同用户校验、完整数据目录摘要、录音 ID 和实例编号共同核对。`TINGJI_CAPTURE_CONTROL_ROOT` 可为隔离测试或短路径覆盖缓存根目录。工作空间索引与写入协调锁另存于空间摘要目录；写入者结束后释放空间锁，旧实例端点保留回执不妨碍下一场立即开始。端点消息有大小及读写等待限制，不能把 PID、遗留 socket 或遗留身份文件当作授权。

API 启动只读发现 broker，不领取控制权、不重放旧命令。初始化阶段若已核对 broker 与持久启动标记，但写入者尚未持锁，仅保留启动观察，不抢先把会话改为中断；真正写盘健康仍依赖文件与心跳。新实例在打开设备前写入 `capture-launch.json`，相同实例禁止重新启动，以免失败恢复变成覆盖旧音轨的新采集。

### 控制租约与命令

- 当前控制者是 API 实例，同一 API 的多个页面共享它，页面间仍使用 A2 录音命令版本协调。默认租约为 10 秒；带有效令牌的状态检查续租，不带令牌的观察不续租。API 正常退出明确释放，异常退出等待租约过期。
- `POST /api/native-capture/{rid}/recover-control` 必须提交观察到的 `expected_generation`。原租约仍有效、代次已变化或采集实例不符时拒绝。领取成功增加代次并签发仅驻留 API 内存的令牌，旧控制者迟到请求被拒绝。浏览器只收到状态，不收到令牌。
- 每次物理命令有请求 ID、当前控制代次及递增序号。先将意图 fsync 落盘再写 stdin，保留最近 64 条回执；重试同一 ID 只返回原回执，不再次发送。响应丢失或未确认不会自动重放。A2 的持久待确认流程继续生效。
- 暂停／继续依据同实例状态确认；停止还要求采集器退出码为零、状态 stopped、无错误或已知失败阶段。缺少文件或异常退出不冒充正常停录。停止未确认时保留待确认及原音轨，不通过旧 PID 强制宣告成功。

本机 socket 以当前登录用户为信任边界，不提供针对同用户恶意进程的隔离。权限令牌不写入诊断或控制记录。

### 故障与生命周期

broker 失败会使子采集器 stdin EOF，按 v1 路径收尾；不自动重启同一实例。停止后的 broker 最多保留约 30 秒供回执查询，然后退出；失效 socket 只能由下一位取得 broker 锁的服务清理。按实例缓存终态与最近 64 条控制回执；服务退出后可只读核对，不能据端点消失编造退出码。缓存暂不自动清理，长期会话回执仍由 A2 数据保存。

启用录音防休眠时，按实例持久化策略，broker 另行持有绑定自身进程的 caffeinate 断言；API 退出不会因此释放它。采集器结束或明确关闭策略后解除。此能力只验证进程归属及策略逻辑，没有实际睡眠唤醒验收。

独立服务还持有数据目录的共享维护租约，离线备份／恢复不能只凭 API 已退出判断空闲；备份另查采集器内核租约。停止后的短暂回执查询窗口仍需等待控制服务退出后维护。

采集继续不代表 ASR 无缝继续。API 启动后 ASR 沿既有检查点及覆盖恢复，模型和设备故障仍独立处理。用户应在工作台明确结束录音；退出宿主或 API 不是结束独立采集。服务管理的强制退出提示已相应说明。

### 验收与后续

使用只依赖 Foundation/CryptoKit 的合成 Swift 写入者，共享真实租约代码。已验证实际 API 进程连续两次被结束／重启后写盘继续、显式恢复、旧控制撤销、重复命令和丢失响应、意图写盘失败、坏端点／用户身份／过期序号、重复服务、broker 崩溃、启动竞态、同实例拒绝重启，以及异常停止证据。

真实麦克风、ScreenCaptureKit 授权交互、三小时长录音、睡眠、设备争用和长时间模型组合仍需独立硬件验证。下一轮收敛运行管理中的 broker 版本／退出原因／未确认提示、服务升级与退出协同，以及恢复后的 ASR 状态闭环；独立发行与公证不在本轮完成。


## E7：运行观察、交付保护与识别恢复

`GET /api/runtime/capture-control` 被动读取最新实例的 broker 构建／源码摘要、启动时间、状态、代次、退出原因和未确认命令计数；无令牌观察不续租。不展示控制令牌，不将 PID 或二进制版本当作授权。状态读取失败时保持原录音状态查询的保守边界，不能推断采集已停止。build 标识属于进程诊断，不是独立发行或签名认证。

build 4 在打开任何采集设备前，以可执行路径的 SHA256 标识取得 `capture-delivery/<hash>/binary.lock` 共享锁（0700 目录、0600 文件、属主／类型校验）。Python broker、试录和 Swift 采集器使用相同路径协议；Swift 自持锁可覆盖控制进程崩溃。事务更新／回退持独占锁贯穿构建核对与原子发布，拒绝活动采集器；旧 build 3 使用进程扫描与父 broker 保护，不能宣称相同的崩溃窗口保证。`TINGJI_CAPTURE_DELIVERY_ROOT` 仅提供本机隔离目录覆盖。

更新不发送停止命令，也不热替换运行中的 broker。先在工作台结束录音及试录，再执行更新；正常服务停止通过内核写入者锁补查忙碌，无法核对时拒绝。退出宿主或强退 API 仍不表示物理采集结束。升级记录、旧二进制和回退日志在本机缓存保留；应用包不包含模型、数据或 Python 环境，不代表公证发行。

`POST /api/recordings/{rid}/live-session/recover` 必须提交当前 `expected_seq`，只恢复无活动任务、仍在采集的原生实时会话。沿用持久配置／确认游标、清除未确认尾部，不自动恢复已结束录音、不重新打开设备。事件循环内核对和调度之间不让出执行权，迟到／重复序号拒绝。原覆盖范围和缺段保留，游标并不表示之前每一秒都覆盖；剩余缺段仍由会后补识别处理。重启／手动恢复标记随新确认结果更新，模型请求不会因单纯打开管理页而启动。

本轮使用合成 PCM、假识别器和无设备 Swift 锁测试；真实录音授权、睡眠／唤醒、设备争用和真实模型追赶质量继续独立验收。


## E8：设备核对和发行预检

设备观察开始即保存运行环境指纹；结束后 `GET /api/runtime/recording-checks/{cid}/acceptance` 提供六场景证据评估，`POST .../acceptance-review` 保存绑定报告／环境的人工通过或未通过。旧观察缺少起始环境记录时不允许补签当前版本通过；新失败不被旧通过遮盖。现场标记、文件增长及计时不自动证明声音完整；原自动硬件验证字段保持 false。

`GET /api/runtime/release-readiness` 集中只读核对已安装组件、默认连接的源码／清单范围及人工设备清单，独立运行环境、Developer ID／公证与干净机器发行仍列未完成；不申请权限、不采集或推理、不停止服务。真实短测和剩余场景、命令行显式选择要求见 [HARDWARE_ACCEPTANCE.md](HARDWARE_ACCEPTANCE.md)。本轮系统音轨回听正常不能替代麦克风语音、三小时、睡眠或真实模型恢复验收。
